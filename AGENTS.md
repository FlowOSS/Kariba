# AGENTS.md

Kariba: Linux security suite unifying external engines (currently ClamAV only) behind a root daemon + thin clients. Early development — `PLAN.md` is the canonical architecture doc; consult it before structural changes. Its workspace/layout diagrams are partly aspirational (e.g. `packaging/`, other engines don't exist yet).

## Commands

- `cargo test --workspace` — fast, no external services required
- Single test: `cargo test -p kariba-core expand_tilde`
- Lint: `cargo clippy --workspace`; format: `cargo fmt` (rustfmt.toml sets edition 2024)
- Run daemon: `cargo run -p karibad`; CLI: `cargo run -p kariba-cli -- survey|status|scan <paths> [--quarantine|--no-quarantine]|quarantine list|restore <id>|delete <id>|threats [--status <s>]|settings|settings set <key> <value>|settings restore-builtins`
- GUI: `cd apps/gui && pnpm install` first (lockfile is pnpm), then `pnpm tauri dev` (starts Vite itself on :1420) and `pnpm check` (svelte-check) for typechecking

## Architecture

- Cargo workspace, Rust edition 2024 (let-chains ok). Binaries: `karibad` (crates/karibad), `kariba-cli` (apps/cli), `kariba-gui` (apps/gui/src-tauri). Libraries: kariba-core, kariba-ipc, kariba-survey, kariba-engine-clamav (crates/engines/clamav).
- IPC is JSON-RPC 2.0 over a Unix socket. Method constants and shared param/result types live in `crates/kariba-ipc/src/protocol.rs` — daemon, CLI, and GUI must all use them. `scan.start` streams `scan.progress`/`scan.detection` notifications before the response arrives.
- Layering rules (from PLAN.md): kariba-core holds facts only (paths, distro/init detection, settings schema), zero policy; kariba-survey adds policy (checks, advice; detects only, never auto-installs); engines depend on core, never on survey.
- GUI: Svelte 5 + Tailwind v4; all daemon access goes through Tauri commands in `apps/gui/src-tauri/src/main.rs`, wrapped in `apps/gui/src/lib/api.ts`. Scan progress reaches the frontend via Tauri events `kariba://scan-progress` / `kariba://scan-detection`. The window is frameless (`decorations: false`); `components/Titlebar.svelte` provides the drag region and window controls (needs `core:window:allow-start-dragging` etc. in `capabilities/default.json`). Bundle is intentionally disabled (`tauri.conf.json`).
- System tray (Tauri `tray-icon` feature, setup in `setup_tray`): state icons green/yellow/red/gray (`icons/tray/`, embedded via include_bytes) from a 5s poller (daemon status + threats newer than 2 min); right-click menu (Open, Quick/Full Scan via the shared `start_scan` helper with daemon-default quarantine, real-time toggle as CheckMenuItem kept in sync by its own poller, Quit); left-click toggles a frameless 360×440 popup window (label `popup`, loads `index.html?mode=popup` → `Mini.svelte` via App.svelte routing, hides on blur/close-request) positioned best-effort near the tray rect (Wayland may reposition it). Main-window close hides to the tray (CloseRequested intercepted, prevent_close + hide); the tray's Quit is the only real exit — don't "fix" close to destroy the window.
- Tray on Linux bypasses tauri's tray backend entirely: tray-icon's libappindicator backend has NO click-event wiring (`rect()` is None, tooltips no-op, clicks can only open the menu), so `src-tauri/src/tray_ksni.rs` owns the StatusNotifierItem D-Bus interface directly via the `ksni` crate (Linux-only dependency). That gets us the real `Activate(x, y)` with screen coordinates: left-click toggles the popup, middle-click opens the main window, right-click shows the ksni menu (Open, Quick/Full Scan, "Real-time protection: on/off" label-toggle, Quit). Icons are the same `icons/tray/` PNGs converted RGBA→ARGB32. The status poller is a plain OS thread (ksni's handle API is blocking — never call it inside the async runtime). Kariba is Linux-only; there is no non-Linux tray path. Popup positioning lives in `src-tauri/src/tray_place.rs`: Wayland compositors ignore xdg-toplevel position requests, so on Hyprland we drive the compositor after mapping via `hyprctl` Lua dispatch — find the popup by window address, `hl.dsp.window.float({action="set"})` (a toggle would un-float), then `hl.dsp.window.move({x,y})` to coordinates computed from the cursor; targeting by address means focus is irrelevant. Everything is best-effort, logged with a `[tray]` prefix; failures degrade to "popup opens where the compositor put it". Other compositors are unpositioned for now (layer-shell is the proper wlroots-wide answer, future work).

## Gotchas

- Paths are privilege-dependent (`kariba_core::paths`): root (euid 0) uses `/run/kariba` + `/var/lib/kariba` + `/etc/kariba/kariba.toml`, non-root uses `$XDG_RUNTIME_DIR` / `$XDG_DATA_HOME` / `$XDG_CONFIG_HOME` fallbacks. Selection is by euid, NOT by directory existence — existence-based probing breaks non-root clients whenever a root daemon also runs on the same machine. Daemons bind their euid-selected socket; the root daemon chmods it 0666 (clamd model), and non-root clients try their own socket first then fall back to `/run/kariba/karibad.sock` (`paths::socket_candidates` + `kariba_ipc::connect_daemon`) — that fallback is how the user GUI reaches the root daemon (required for real-time protection); don't regress to single-path connects. polkit gates this in the packaging phase; until then any local user can reach the root daemon's IPC.
- Scanning goes through clamd INSTREAM (karibad reads the file, streams bytes) because clamd runs as the `clamav` user and cannot enter mode-700 home directories — path-based SCAN silently misses private homes. Keep `scan_path` streaming-first; files over 25 MB (clamd StreamMaxLength) can't be streamed, so they're copied to `/tmp/kariba-bigscan` (0644) and SCAN'd as the copy — never regress to path-SCAN of the original, it EACCES inside private homes. INSTREAM replies are NUL-terminated (`stream: OK\0`) — `parse_scan_response` strips the NUL; don't regress it.
- `karibad` must be running for everything except `kariba-cli survey`, which runs locally without the daemon.
- Real scans need a running `clamd`. Dev boxes: Artix/OpenRC (`clamav` + `clamav-openrc` separately) and Arch/systemd (plain `clamav`; enable `clamav-daemon.service` + `clamav-freshclam.service`). Socket `/run/clamav/clamd.ctl` on both. EICAR is the end-to-end detection test vector.
- To run `karibad` as root without creating root-owned files in `target/`, build as the user first (`cargo build -p karibad`), then `sudo ./target/debug/karibad`; run the CLI with the same privilege level or socket paths won't match.
- Quarantine invariants (tested in crates/karibad/src/quarantine.rs): quarantined files are mode 000, restore round-trips byte-identical. Don't weaken these.
- Settings: karibad owns the TOML config (`/etc/kariba/kariba.toml` root, `~/.config/kariba/kariba.toml` user) and writes defaults on first start; `settings.set` is whole-document (get → modify → set), validates, persists atomically, then applies. The scanner snapshots exclusions into a `ScanPolicy` per scan; `ScanParams.quarantine = None` means "use `scan.default_quarantine`". The quarantine dir itself is skipped structurally — never make it a setting. Built-in exclusions (`/proc /sys /dev /run`) are ordinary config entries the user may remove (GUI warns); don't re-hardcode them. `realtime.enabled` is persisted intent — the fanotify slice must read it rather than adding a new flag.
- NVIDIA + Wayland crashes WebKitGTK at startup ("Gdk Protocol error 71") and XWayland renders a solid color there, so neither native DMABUF nor X11 fallback works on NVIDIA. `kariba-gui` auto-sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` when NVIDIA + Wayland is detected (`apply_nvidia_wayland_workaround` in apps/gui/src-tauri/src/main.rs); don't remove it without a replacement.
- PLAN.md "Known Issues / Follow-ups" lists accepted bugs (sequential scan throughput is the main one). Check there before diagnosing scan behavior as new. All GUI Tauri commands are async (`spawn_blocking`) and the scanner takes short-lived DB locks — keep it that way so the UI stays responsive mid-scan. `scan.cancel` plus dead-client detection (failed notification sends) abort scans server-side; don't reintroduce orphaned scans.
- Real-time protection (crates/karibad/src/{fanotify,realtime}.rs): fanotify needs CAP_SYS_ADMIN, so it only runs in the root daemon; a user-mode daemon reports `realtime_active=false` with the reason — that's graceful degradation, not a bug. Watcher design rules: exec verdicts are bounded (`VERDICT_TIMEOUT`, per-batch `VERDICT_BATCH_BUDGET`, fresh clamd connection per verdict) and FAIL OPEN on timeout/engine-down/budget + re-queue the path — permission events must never wait unboundedly, and the ALLOW/DENY response is written BEFORE any bookkeeping (quarantine/DB/broadcast run through the worker queue afterwards); the kernel queue is BOUNDED (no `FAN_UNLIMITED_QUEUE` — an unlimited queue plus any reader stall pins one fd+inode per event system-wide and froze a machine once), overflow arrives as `FAN_Q_OVERFLOW` and is logged + surfaced in status; intake closes event fds immediately and never does I/O (overflow goes to an in-memory spill buffer that a spill thread batches into the `pending_scans` SQLite table in transactions — never put disk I/O on the intake path); close-write paths enter a dedup'd memory queue capped at 50k; spilled backlog stays in the DB and is drained in batches ONLY when the live queue is empty, so fresh events always jump ahead of stale backlog (reloading the whole backlog into memory at start is a priority bug — done once, fixed); a watchdog thread checks the intake heartbeat and on a >3s stall closes the fanotify fd (kernel auto-allows all pending permission events) and restarts the watcher, failing open visibly after repeated stalls; shutdown closes the fanotify fd FIRST, persists the queue, interrupts workers via their registered clamd socket handles, then joins (never drain-scan the backlog on shutdown); 4 workers (30s read timeout) drain the queue while the exec gate stays synchronous as the backstop; errors are suppressed per path for 60s and EMFILE backs off 200ms; progress is logged every 5k scans with backlog/rate/ETA; marks are released by closing the fanotify fd (no unmark calls); the watcher is restarted (not mutated) on every `settings.set` via `Daemon::sync_realtime`; exclusions + quarantine dir + data dir + clamd DB dir are snapshotted at watcher start; writes by clamd/freshclam/karibad (checked via /proc/pid/comm) and already-deleted files are skipped; detections broadcast through the Broadcaster to all registered connections (the GUI keeps one persistent subscriber connection via the `realtime_events` command). Real-time detections are grouped under a sentinel `realtime` scan row. Semantics: detection ALWAYS happens when real-time is on; `realtime.auto_quarantine` only chooses the response — daemon logs spell it out ("quarantined" / "left in place (auto-quarantine is off)" / "quarantine FAILED"), GUI action labels are `detected|quarantined|denied|denied+quarantined`. See PLAN.md "Real-time Protection Design".

- `apps/gui/src-tauri/gen/schemas/` is generated and gitignored; never commit it.
